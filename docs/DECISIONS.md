# Design decisions

Short entries, newest last. Each says what was decided and why.

## D-001 — Phase 0: package layout and tooling (2026-11-19)
`src/` layout, setuptools backend, `pyproject.toml` holds ruff/mypy/pytest config.
Tests marked `integration` (network, local Ollama, broker sandbox) are skipped by default.

## D-002 — Dependencies (2026-11-19)
Core: `pydantic` (contracts), `PyYAML` (guardrails), `python-dotenv` (`.env` secrets),
`httpx` (HTTP clients incl. Ollama), `tenacity` (retries, Phase 1).
Optional extras so nothing is installed before it's needed: `anthropic`, `graph`
(LangGraph), `rag` (ChromaDB), `brokers` (alpaca-py, mcp). Dev: pytest, pytest-asyncio,
hypothesis, ruff, mypy, types-PyYAML.
Ollama is reached via plain `httpx` against `/api/chat` rather than the `ollama` package,
which saves a dependency and lets tests use `httpx.MockTransport`.

## D-003 — 5% position cap is a hard ceiling in the config validator (2026-11-19)
The governance plan calls ≤5% equity per ticker a hard cap. `config.py` rejects
`max_position_pct > 0.05` (and requires pilot caps ≤ main caps). Config can be stricter,
never looser. Constant `HARD_CEILING_POSITION_PCT` is the one policy number in code.

## D-004 — `orders.allowed_types` may only contain `limit` (2026-11-19)
Typed as `list[Literal["limit"]]`, so listing `market`/`stop` fails at load. The broker
adapter rejects non-limit orders again in Phase 2 (defense in depth).

## D-005 — `residual_scenario_return` must be in [-1.0, 0.0] (2026-11-19)
A collapsed/pruned scenario is meant to be conservative, so it may not be a gain.
The actual value (-0.70) is still a PLACEHOLDER to decide before Phase 5.

## D-006 — ScenarioSet carries its tolerance explicitly (2026-11-19)
`ScenarioSet(scenarios=..., tolerance=cfg.tot.prob_sum_tolerance)`. Keeps schemas free
of config imports and avoids a hidden default tolerance. Scenarios in a set are terminal
outcomes with *joint* probabilities; `ToTNode.probability` is conditional on its parent.

## D-007 — Audit log is hash-chained in addition to triggers (2026-11-19)
Triggers block UPDATE/DELETE through SQLite. A SHA-256 chain (`prev_hash`, `entry_hash`)
makes tampering outside SQLite (dropping triggers, editing the file) detectable via
`verify_audit_chain()`. Payloads are redacted before hashing and writing.

## D-008 — LLM switcher built in Phase 0, not Phase 5 (2026-11-19)
The user wants to swap between local (Ollama) and hosted models, so `agents/llm.py`
landed early. Spec `<provider>:<model>`, per-role env overrides
(`BIOTRADEAI_LLM_RESEARCH`), default `anthropic:claude-sonnet-5-5` per the plan.
All prompts pass through `redact_text` before leaving the process.

## D-009 — Monetary values use `Decimal` (2026-11-19)
`limit_price` is `Decimal` (≤4 dp) so approval-token signatures are canonical and free of
float rounding (`4.5` and `4.5000` sign identically).

## D-010 — Phase 1: runway definition (2026-11-19)
Liquidity = cash & equivalents + current + non-current marketable securities, one tag
per group via a fallback chain (never summed across tags, so no double counting).
`LongTermInvestments` is excluded because it can include strategic equity stakes.
Quarterly burn = max(latest quarter, mean of last `runway.burn_lookback_quarters`, 0):
conservative for a veto because a rising burn is not averaged away. If no discrete
quarter can be derived, annual operating cash flow / 4 is used and noted.

## D-011 — New config key `runway.burn_lookback_quarters: 4` (2026-11-19)
Not in the original plan. The burn window is a threshold-like knob, so it belongs in
guardrails.yaml rather than as a code default.

## D-012 — Duplicate/restated XBRL facts (2026-11-19)
For the same (start, end) period the fact with the latest `filed` date wins, ties broken
by accession number. Restatements therefore always win, and any change in value is
recorded in `RunwayResult.notes`. `as_of` drops facts filed after that date, which is
the basis for point-in-time backtests (Phase 7).

## D-013 — Synthetic EDGAR fixtures (2026-11-19)
The 10 runway fixtures are synthetic companies (CIK 9000001–9000010) shaped exactly like
real companyfacts JSON, generated by `scripts/build_edgar_fixtures.py`. Expected values
are worked out by hand in `data/fixtures/edgar/expected_runway.yaml`. Each one exercises an
edge case: YTD differencing, restatement, duplicates, missing securities, a fallback tag,
cash-flow positive, annual-only, no data, a missing quarter, plus the dilution trap.
Real tickers are added once `data/catalysts.csv` is seeded. A live integration test checks
the parser against real SEC data.

## D-014 — TTL means fetch freshness (2026-11-19)
`ttl_hours` limits how long ago a record was *fetched* (inclusive boundary, with 5 minutes
of tolerated clock skew for future timestamps). Fundamental data is always weeks old; its
age is visible through `balance_sheet_date`, not through the TTL.

## D-015 — CT.gov dates are claims (2026-11-19)
`ClaimedDate` keeps precision (day/month), kind (ACTUAL/ANTICIPATED) and the raw string.
Catalyst dates come only from the human-curated `data/catalysts.csv`.

## D-016 — Retry/rate limiting with tenacity (2026-11-19)
Retries on 429/5xx/transport errors with exponential backoff; 404 and other 4xx fail
immediately. EDGAR is capped at 8 req/s (SEC ceiling is 10), shared across sec.gov hosts.

## D-017 — Phase 2: Alpaca via REST + httpx instead of alpaca-py (2026-11-19)
The adapter needs six endpoints. Plain `httpx` adds no dependency, works on Python 3.14,
and lets tests use `httpx.MockTransport`, the same pattern as the data clients. Order POSTs
are never retried automatically, since a retry could duplicate an order;
`client_order_id = btai-<approval nonce>` makes a manual re-submit idempotent at Alpaca.
`alpaca-py` stays listed in the `brokers` extra in case it is needed later.

## D-018 — Robinhood adapter ships mode gating only (2026-11-19)
Per "do not invent API fields", the field mapping for each Robinhood MCP tool waits for the
Phase 3 spike. Already in place: `verify_tools()` against `list_tools`, limit-only
rejection, shadow-mode `place_order` raising *before* any MCP call, and redaction of every
tool result. Unmapped calls raise `SchemaNotVerifiedError`.

## D-019 — New config key `orders.approval_ttl_minutes: 15` (2026-11-19)
How long a human approval stays valid. Short, so an approval can't be replayed hours later
at a stale price. Capped at 60 minutes by the validator.

## D-020 — Rule boundary conventions (2026-11-19)
Minimums pass at the threshold (EV, runway veto, confidence); maximums pass at the
threshold (position cap, spread). The drawdown limit trips only when exceeded. The fatal
runway prune fires strictly below `fatal_runway_months`. TTL is inclusive.

## D-021 — Execution check order and scope (2026-11-19)
In order: kill-switch -> mode (live blocked until Phase 10) -> order type -> approval token ->
fresh broker state (blocked account, drawdown, position cap including existing exposure,
concurrency, no shorting, spread and quote TTL for buys only) -> nonce consumed -> place
(paper) or review (shadow). Spread is not checked on sells, because an exit must never be
blocked by an illiquid book. Policy refusals (`OrderRejectedError`, `ShadowModeError`) do
not count toward the kill-switch's API-error streak; real broker failures do.

## D-022 — Live mode uses pilot caps (2026-11-19)
`rules.effective_limits` returns `live_gate.pilot_position_pct` / `pilot_max_positions` in
live mode. Execution currently rejects live mode outright; the live gate lands in Phase 10.

## D-023 — Architecture tests (2026-11-19)
`tests/unit/test_architecture.py` parses `src/` with `ast` and fails if `place_order` is
called anywhere except `brokers/execution.py`, or if `agents/` or `graph/` import
`biotradeai.brokers`.

## D-024 — Robinhood work moved to the final stage (2026-11-19)
At the user's request, Phase 3 (Robinhood spike), Phase 9 (shadow) and anything else that
needs the user's own accounts move to the very end. The order is now
0 → 1 → 2 → 4 → 5 → 6 → 7 → 8 (Alpaca paper) → 3/9/10 (Robinhood).

## D-025 — Phase 4 recall target: recall@5 >= 0.90, zero bleed (2026-11-19)
Agreed with the user before coding. Measured on `data/fixtures/rag` (30 synthetic drugs,
61 queries, 391 docs incl. risk-sounding boilerplate distractors and cross-ticker bait).
Enforced by `tests/eval/test_recall.py`, which runs whenever the model is cached.

## D-026 — Default embedder: BAAI/bge-small-en-v1.5 (2026-11-19)
The user first picked all-MiniLM-L6-v2. It scored recall@5 = 0.885 (0.893 hybrid), with
every miss on vague queries. bge-small-en-v1.5 scored 1.000 with or without hybrid.
The user approved switching the default; MiniLM stays available via `BIOTRADEAI_EMBEDDER`.
BGE query instructions are applied to queries only (`embed_queries`).

## D-027 — Hybrid retrieval (BM25 + cosine, Reciprocal Rank Fusion) on by default (2026-11-19)
`rag.hybrid: true`. It runs only inside the already-filtered ticker+entity pool, so it
can't widen what is retrievable. Search within the pool is exact (no ANN approximation)
up to `rag.max_pool` chunks. The similarity reported for confidence is always cosine.

## D-028 — Claims are regex-extracted and hedge-filtered (2026-11-19)
Conflict detection compares four claim types (clinical_hold, primary_endpoint,
pdufa_date, crl) pulled from factual sentences only. Hypothetical risk-factor language
("may", "could", "if", "no assurance", ...) is ignored, so a 10-K saying "we could
receive a CRL" is not a CRL claim. An LLM extractor may be added later behind the same
interface.

## D-029 — Tier conflict rule (2026-11-19)
Per claim key, each tier's most recent claim is taken. The most authoritative tier wins,
EXCEPT when a Tier-2 claim is at least as recent as the Tier-1 winner and disagrees with
it: that is "unresolved" and makes the bundle INCONCLUSIVE. An older Tier-2 claim is
superseded by a newer Tier-1 record, so stale 10-K text can't block a ticker forever.
Within one tier, the most recent claim wins.

## D-030 — Confidence = authority x density (2026-11-19)
authority = similarity-weighted mean of `rag.tier_weights` (1.0 / 0.85 / 0.6) over
chunks with cosine >= `rag.min_similarity`; density = min(1, relevant /
`rag.min_supporting_chunks`). Consequences: one chunk alone is never enough (0.5x), and
press/PubMed-only evidence (0.6) is always below `min_confidence` 0.70, so it escalates.

## D-031 — Strict entity filter; company-level text has its own entity (2026-11-19)
Retrieval filters on exact ticker AND entity_id, as the plan says. Chunks that name no
known drug get `ENT-<TICKER>-COMPANY` and are retrievable only by asking for that entity
explicitly. Chunks that name several drugs are stored once per drug.

## D-032 — New dependencies for RAG (2026-11-19)
`rag` extra: chromadb (vector store), sentence-transformers (local embeddings), pypdf
(FDA briefing PDFs). Ollama embeddings use plain httpx. PubMed XML is parsed with the
stdlib ElementTree from the trusted NCBI host; modern expat refuses entity-expansion bombs.

## D-033 — Phase 5 inputs: defaults used, all open for review (2026-11-20)
The user said to start Phase 5 without choosing the three open inputs, so these
defaults were used. Each is easy to change:
* Research model: any spec via `--llm`, `BIOTRADEAI_LLM_RESEARCH`, `BIOTRADEAI_LLM_CRITIC`.
  Tested with scripted replies (offline) and with `ollama:llama3.2:3b`. The code default
  stays `anthropic:claude-sonnet-5-5`.
* `tot.residual_scenario_return` stays at the -0.70 PLACEHOLDER.
* `data/base_rates.yaml` is seeded from BIO/Informa/QLS 2021 (Phase III -> NDA/BLA 57.8%,
  NDA/BLA -> approval 90.6%) and has `reviewed: false`. How partial outcomes are split
  off, and every return figure, are labelled ASSUMPTIONS in the file. Until a human sets
  `reviewed: true`, every run logs a warning.

## D-034 — ToT shape and bounded adjustments (2026-11-20)
Depth 1 is the clinical outcome (success/partial/failure, always all three). Depth 2 is
the regulatory reaction given that outcome. Depth 3 is financing/dilution, bucketed by
runway computed in code. The LLM may propose an adjustment of up to +/-
`tot.max_prob_adjustment` per outcome. Code clips each proposal to that band. It then
applies one common shift, clipped to each outcome's box, so siblings sum to exactly 1
(`agents/tot.bounded_projection`). The base rate, final probability, adjustment,
justification and evidence hashes are logged for every node.

## D-035 — Returns come from base_rates.yaml, never from the LLM (2026-11-20)
Each node carries a `step_return` from the base-rate file. A leaf's return is the
product of (1 + step) along its path, minus 1, floored at -100%. The LLM prompt contains
no return figures (a test enforces this). MUST #5 covers EV inputs as well as EV itself.

## D-036 — Beam-cut branches also go into the residual (2026-11-20)
Plan correction #2 says pruning only saves compute. A depth-1 outcome outside the beam
(width 2) is therefore not dropped. It is collapsed into the single residual scenario at
`residual_scenario_return`, together with fatal-flaw prunes, so EV always covers 100%
of the probability mass.

## D-037 — Fatal flaws collapse every non-failure branch (2026-11-20)
An active clinical hold (resolved RAG claim) or runway below `fatal_runway_months`
(strictly below, as in Phase 2) marks success and partial as pruned with the reason
stated. Only the failure branch is kept and expanded.

## D-038 — The Critic can only make the tree more conservative (2026-11-20)
* Deterministic groundedness rule: an adjustment that cites no valid evidence id is
  rejected without asking the LLM. Unknown evidence ids are dropped; the LLM sees short
  ids (E1..En) that map back to sha256 hashes in code.
* The critic LLM says accept or reject for each adjustment. A missing verdict, an
  unparseable reply or an LLM error all count as reject.
* An unparseable generator reply means base rates are used.
So a weak or failing model degrades the tree to base rates. It never makes it bolder.

## D-039 — Risk Agent is fully deterministic (2026-11-20)
The plan says "mostly deterministic". This implementation uses no LLM at all.
* EV is recomputed with `rules.compute_ev` over the flat ScenarioSet. The Research
  Agent computes EV with a separate depth-first walk of the tree (`tot.tree_ev`).
* A gap larger than the new config key `tot.ev_match_tolerance` (0.0001) is logged as
  `risk.ev_mismatch` and vetoes the trade.
* Extra checks beyond the plan's list: evidence status, room under the position cap at
  a limit price equal to the ask, TTL on quote/runway/portfolio/evidence, and that the
  catalyst date has not passed.

## D-040 — Supervisor on LangGraph 1.x (2026-11-20)
Graph state is a TypedDict of JSON-serialised contracts (CatalystState,
ResearchInputs, ToTNode). Every node re-validates them through Pydantic before acting
and before returning, so a transition cannot emit an invalid state.
* INCONCLUSIVE evidence routes straight to human review before any LLM call.
* HITL uses `interrupt()`. The CLI issues the HMAC approval token and resumes the
  graph with it.
* Execution is an injected callable wired to `brokers/execution.py`; the graph package
  never imports `biotradeai.brokers`.
* Checkpoints live in `data/checkpoints.db` (git-ignored). A run waiting for approval
  survives a restart (tested).

## D-041 — New dependencies: langgraph, langgraph-checkpoint-sqlite (2026-11-20)
`graph` extra: `langgraph>=1.0` (state machine, interrupt) and
`langgraph-checkpoint-sqlite>=3.0` (durable checkpoints). LangGraph pulls in langsmith.
LangSmith tracing is OFF unless `LANGSMITH_TRACING` / `LANGCHAIN_TRACING_V2` is set.
Do not set those: they would send prompts to an external service.

## D-042 — `evaluate` on fixtures is a dry run at simulated time (2026-11-20)
`data/fixtures/scenarios/*.yaml` runs the real claim extraction, conflict resolution
and runway math. The run uses an in-memory FakeBroker and clock = the fixture's
`as_of`. Building inputs from live retrieval, EDGAR and broker quotes
(`biotradeai/inputs.py`) is written, but it is wired into a CLI command in Phase 8, once
Alpaca keys exist.

## D-043 — trailing_stop_pct stays at the 0.10 PLACEHOLDER (2026-11-20)
The user started Phase 6 without choosing a value, so 10% below the high-water bid is
used. Change `sell.trailing_stop_pct` in config to set it deliberately.

## D-044 — Sell machine is plain Python, not LangGraph (2026-11-20)
The sell side has no LLM, no branching on model output and no human pause, so a pure
function `step(position, event, cfg)` is simpler to test and replay than a graph. It
still lives in `graph/sell_graph.py` as the plan's layout says. `SellEngine` writes
every exit and state change to the audit log, and saves position state in a new
`sell_state` table.

## D-045 — How the sell triggers were interpreted (2026-11-20)
* Run-up: sells 100%, and only on ticks dated strictly before the catalyst date. It
  fires AT the target (bid >= entry x 1.30). The bid is used because that is the
  price we could sell at.
* Readout: `positive` sells floor(qty x scale_out_fraction), at least 1 share, then
  trails the rest. `negative`, `crl` and `mixed` sell 100%. Mixed counts as a failure
  because it is the conservative choice.
* Trailing stop: the high-water mark is the highest bid since the readout, starting at
  the last bid. It fires AT high x (1 - trailing_stop_pct).
* Time-stop: the slip is measured from the primary completion date at entry, so it
  adds up across several slips. A month is 30.44 days. It fires only when the slip
  strictly EXCEEDS completion_delay_months.
* "Never hold between Phase 2 and Phase 3 readouts": when a `catalyst_scheduled` event
  arrives while the remainder is being trailed, the remainder is sold. A new trade must
  then come from a fresh buy evaluation.

## D-046 — Exit orders: SELL LIMIT at the bid, staged only (2026-11-20)
The limit price is the last bid rounded down to the cent, which is marketable but is
never a market order. Every exit order is checked with `rules.check_order_type`. An
exit that comes before any quote is logged as `needs_quote`, with no price. Exits are
staged; placing them goes through `execution.py` with an approval token, which is
wired in Phase 8. Open point for Phase 8: whether urgent exits (CRL, dilution) need
the same typed approval as buys.

## D-047 — What counts as a dilutive filing (2026-11-20)
* By form alone: S-3, S-3ASR, S-3/A, S-1, S-1/A and 424B1-5. The plan names S-3;
  S-1 and 424B prospectus supplements are added because they are the same event,
  so this errs toward selling.
* An S-3 that only registers resales by existing holders also triggers. That is
  conservative.
* An 8-K counts only if its text names an equity offering (underwritten, registered
  direct, ATM, private placement, pre-funded warrants, sale or issuance of shares).
  This is checked with a regex in `events.classify_filing`.

## D-048 — Pollers (2026-11-20)
* `data/pollers.py`, FilingPoller: reports each EDGAR accession once, tracked in a new
  `seen_filings` table. It downloads only 8-K documents, to stay within SEC's rate
  limit.
* TrialDatePoller: compares the CT.gov primary completion date with `evaluated_ncts`.
  The first sighting only records the baseline.
* No new dependencies.

## D-049 — Backtest data is synthetic for now (2026-11-20)
`data/fixtures/backtest/cases.yaml` holds 12 labelled cases and is generated by
`scripts/build_backtest_fixtures.py`.
* They cover strong and weak Phase 2 evidence, both outcomes, two Tier-1 vs Tier-2
  clinical-hold conflicts, a 1-month-runway trap and a PDUFA case.
* Every case also has a "leak" press release, dated after the decision, that states the
  real outcome.
* These cases prove the harness and metrics work. They do NOT measure real predictive
  skill: a Brier score on synthetic labels means nothing about real catalysts. Real
  historical cases need the user's catalyst list (open question 1). The harness reads
  any YAML in the same format via `--cases`.

## D-050 — Point-in-time enforced twice (2026-11-20)
1. The retriever's metadata filter `published_ts <= as_of` (from Phase 4).
2. The harness re-checks every hit and every bundle source. Anything dated after the
   decision time raises `PointInTimeViolationError`, and the case is counted as a leak.
The leak document is ingested into the same index on purpose, so a broken filter
would surface it. A test also queries with the leak's own wording to prove it would
otherwise be the top hit.

## D-051 — How each metric is defined (2026-11-20)
* Brier: (P(clinical success) at depth 1 after the critic − outcome)², averaged over
  cases that built a tree. INCONCLUSIVE cases have no tree, so they are excluded. The
  report also shows the base-rates-only Brier as a reference.
* Groundedness: share of (a) resolved claims whose source hash is in the evidence
  bundle, (b) LLM adjustments that cite evidence in the bundle, (c) runway figures
  with filing accession numbers.
* Guardrail breaches: recomputed in `backtest/metrics.py` from raw state, separately
  from the Risk Agent, so a Risk Agent bug would show up as a breach.
* Escalation accuracy: share of expected-conflict cases routed INCONCLUSIVE. False
  escalations are listed separately.
* Latency: wall time per case from retrieval to decision. The graph stops at the
  approval interrupt, so no human wait is included.
* `backtest --llm base` (the default) runs with no LLM adjustments. This is the
  baseline any model must beat.

## D-052 — Fix: code rebalancing is not an LLM claim (2026-11-20)
The backtest found a Phase 5 bug. When a large adjustment hits the [0, 1] box (e.g. a
PDUFA failure base rate of 0.094 moved by −0.15), the rebalancing step moves an
untouched sibling. The critic then treated that shift as an LLM claim with no evidence
and labelled it "rejected", which was misleading.
* Fix: only adjustments the LLM actually proposed are reviewed or counted for
  groundedness (`research.is_llm_adjusted`).
* Siblings moved only by code are labelled "base rate (moved only by rebalancing…)".
* Regression test added.

## D-053 — No new dependencies for Phase 7 (2026-11-20)
The backtest uses chromadb's in-memory client, the existing embedders and LangGraph's
in-memory checkpointer. Reports go to `reports/` (git-ignored) as Markdown + JSON.

## D-054 — Phase 8 is built and tested without the user's keys (2026-11-20)
The user will add keys later. Alpaca has no public test keys, and creating an account
is the user's step, so no "temporary keys" were used.
* The real `AlpacaBroker` code is tested against a mock Alpaca server (MockTransport)
  using dummy key strings. The test checks the exact POST body (limit, DAY, no
  extended hours), and checks that the account number and secret never reach the
  audit log.
* Everything else runs against FakeBroker.
* The 8-12 week paper run itself starts once `.env` has `ALPACA_API_KEY/SECRET`,
  `APPROVAL_HMAC_SECRET` and `SEC_USER_AGENT`, and `data/catalysts.csv` has tickers.

## D-055 — Paper cycle design (2026-11-20)
* `paper run` does one cycle and exits; schedule it with Task Scheduler or cron. No
  daemon. Exits run before entries.
* An unfilled open BUY order counts as exposure (concurrency and position cap), so
  re-running a cycle cannot stack orders.
* Each ticker is evaluated at most once per day; the date comes from the cycle's own
  clock in the run id.
* After every placed buy, an independent post-trade check runs. A breach writes
  `guardrail.breach` and trips the kill-switch.

## D-056 — Exits need the same typed human approval as entries (2026-11-20)
Open question from Phase 6. The default is the stricter option: every exit goes through
an approval token and `execution.py`, so the agent never sells on its own. The
consequences:
* A tripped kill-switch also blocks exits (the Phase 2 behaviour).
* An exit that is rejected or doesn't fill is flagged every cycle afterwards
  (`paper.exit_unfilled`) for manual review. It is not automatically re-submitted.
Revisit if urgent exits (CRL, dilution) should skip the prompt.

## D-057 — Readout outcomes come from a human-curated data/outcomes.csv (2026-11-20)
Columns: ticker, drug, date, result (positive|negative|crl|mixed), source_url. Like
catalysts.csv, code never infers what happened at a readout. An outcome is applied to
a position if its date falls between 14 days before the listed catalyst date and today.
A later catalysts.csv row for a held ticker is fed in as `catalyst_scheduled`, which
triggers "never hold between readouts".

## D-058 — Live gate, paper condition (2026-11-20)
`paper gate` counts UTC days with at least one completed `paper.cycle_done` and all
`guardrail.breach` events. It is eligible when days >= `live_gate.min_paper_days` (90)
and breaches == 0. `paper review` summarises one day: decisions, orders placed and
rejected, exits, skips, breaches, kill-switch events and the audit hash chain.
Limitation: time-stop polling needs an NCT id per position, which catalysts.csv does
not have yet, so the CT.gov date poller is not wired into the paper cycle.

## D-059 — Network guardrails for every outbound data request (2026-11-20)
Agreed with the user before building the scout: use only sanctioned access, never
overload a provider, and never send short bursts of requests.
`data/netpolicy.py` + `data/http.py` enforce:
* a host allowlist, also checked on redirects (official APIs only: SEC, ClinicalTrials.gov,
  NCBI, openFDA, Alpaca, Robinhood MCP, plus `*.test`/localhost for tests);
* one shared, jittered rate limiter per source, at about half the published limit;
* a daily request budget per source, persisted in SQLite (`request_ledger`);
* a circuit breaker after 3 failures in a row that switches the source off for the
  rest of the UTC day, logged as `network.source_off`;
* `Retry-After` honoured (capped at 300 s), exponential back-off, other 4xx never
  retried.
A test fails if any URL host in `src/` is not on the allowlist, except citation-only
links.

Rates changed: SEC 8 → 5 req/s; ClinicalTrials.gov 3 → 0.8 req/s; NCBI 3 → 2 req/s
(5 with `NCBI_API_KEY`). openFDA is set to 1 req/s with a 500/day budget (50,000 with
`OPENFDA_API_KEY`). Alpaca gets the allowlist and a 1 req/s limiter but **no daily
budget**, so exits can never be blocked by it.

Sources checked on 2026-11-20:
* SEC: https://www.sec.gov/os/accessing-edgar-data
* NCBI: https://www.ncbi.nlm.nih.gov/books/NBK25497/
* openFDA: https://open.fda.gov/apis/authentication
* ClinicalTrials.gov publishes no number; ~50/min is the most conservative figure
  cited by third parties.

## D-060 — Balanced pacing for bulk jobs, not just off-peak timing (2026-11-20)

## D-063 — One approval covers the drug until one full quarter after launch (2026-11-20)
The user chose drug-lifetime approval over per-catalyst approval. The entry pauses for
re-approval on:
* acquisition or merger;
* licensing of the drug;
* a clinical hold;
* a terminated, withdrawn or suspended trial;
* delisting (Form 25);
* the yearly check-in;
* FDA approval with no launch after ~6 months;
* the first full calendar quarter after launch being reported (a 10-Q/10-K filed after
  that quarter's end).
It retires automatically only when the company says development is discontinued.
Paused entries get no new buys; the sell machine still sees their outcomes. Fiscal
quarters are approximated by calendar quarters.

## D-064 — Agent-managed catalyst events replace human-curated dates for approved pairs (2026-11-20)
This deviates from plan correction #3 (human-curated catalyst dates), at the user's

## D-065 — Scout and follow-loop signal sources (2026-11-20)
* SEC daily form index (`/Archives/edgar/daily-index/YYYY/QTRn/form.YYYYMMDD.idx`):
  one file per business day instead of per-company polling.
* Company records cached for 30 days. Biotech = industry codes 2834, 2836 or 8731, and
  listed on Nasdaq, NYSE or NYSE American.
* 8-Ks are read as the full submission `.txt`, because the catalyst sentence usually
  lives in the press-release exhibit (EX-99.1).
* ClinicalTrials.gov: Phase 3, industry-sponsored, primary completion 60–365 days out,
  using `filter.advanced` (verified live). Sponsors are matched to SEC company names
  (exact, or a unique partial match); the match type is shown on the card.
* Ranking favours: two agreeing sources, an exact date, a PDUFA, runway ≥ 12 months,
  and few Phase 3 trials (sponsors with more than 10 are penalised as diversified).
  Red flags lower the score.
* Soft cap of 30 approved+paused pairs, and at most 10 proposals per run.
* Text signals (`data/signals.py`) are regex only, with hedged sentences ignored.
  Their known weakness is drug naming: codes need two or more digits, and generic
  names are guessed from common drug-name endings. That's why every card shows the
  source sentence.

## D-067 — Scout filters tightened after the first live run (2026-11-20)
The first live run (2 days of SEC filings, 643 Phase 3 trials) proposed large
profitable companies and listed a competitor's comparator drug among a sponsor's drug
names. Fixes:
* Companies that aren't burning cash are filtered as "profitable" (large or diversified;
  one catalyst rarely moves them).
* With `--with-quotes`, companies with a market cap above $10B are filtered too.
* Companies whose runway can't be computed (e.g. foreign IFRS filers) are filtered: the
  Risk Agent would veto them anyway.
* From a trial, only the first (investigational) intervention and its listed other names
  become the drug's names. Comparators and combination partners are shown on the card
  as "given with", and doses, pure numbers and 2–3 letter abbreviations are dropped.
* IDs are tidy (`TICKER:CODE`, no spaces or brackets).
* The card says whether a company-stated date exists yet; ClinicalTrials.gov-only
  proposals become tradable only once a filing gives a date.
* The shortlist enriched per run is 4× the proposal cap, so filtering still leaves
  enough candidates.

Result of the second live run: 5 profitable and 2 runway-unavailable companies were
filtered out, and 3 small/mid-cap pairs were proposed. With the company cache warm,
the run took about 25 seconds.
